What “fixed” means here, precisely

Nothing is fixed in upstream. The original sources are never edited — they are the numerical oracle the port is verified against, and editing them would destroy the only independent check the project has. Every user of the official C library still has all five.

Of the six, four were not fixed so much as made unrepresentable. No patch was written for UPSTREAM-1, -2, -3 or -6; the types stopped permitting them. A month that cannot be 13. A result that cannot carry a sentinel. A period type normalised at construction. A loop whose bound is derived rather than hoped for. That is the strongest single argument for the port existing: four of six defects died as a side effect of choosing better types and stating preconditions, not as a side effect of hunting for bugs.

UPSTREAM-4 is the only defect the port consciously declines to reproduce. Faithfully reproducing a buffer overflow is not fidelity.

UPSTREAM-5 is the only one deliberately kept, because its output is observable by callers; abbreviating "14D" to "2W" would be a behaviour change dressed up as a fix.

UPSTREAM-3

Lowercase 'y' advances a date quarterly, not annually

High · silent mispricing Cannot occur in the port

lib/src/ldate.c · JpmcdsDtFwdAny

Mechanism

Inside case 'Y': the month multiplier is chosen like this:

if (upperPrdTyp == 'M')
    intval.prd = interval->prd;
else if (upperPrdTyp == 'A' || interval->prd_typ == 'Y')   /* raw, not upper-cased */
    intval.prd = interval->prd * JPMCDS_MONTHS_PER_YEAR;
else if (upperPrdTyp == 'S')
    intval.prd = interval->prd * JPMCDS_MONTHS_PER_SEMI;
else
    intval.prd = interval->prd * JPMCDS_MONTHS_PER_QUARTER;  /* 'y' lands here */

The second test checks the upper-cased type for 'A' but the raw type for 'Y'. A lowercase 'y' matches neither, falls to the else, and is multiplied by 3 instead of 12.

Evidence

Start date 2008-01-03, one period, measured against the live library:

  type   upstream       months advanced
  'Y'    2009-01-03     12
  'y'    2008-04-03     3
  'A'    2009-01-03     12
  'a'    2009-01-03     12
  'M'    2008-02-03     1
  'm'    2008-02-03     1
  'S'    2008-07-03     6
  's'    2008-07-03     6
  'Q'    2008-04-03     3
  'q'    2008-04-03     3

'y' is the only period type in the library whose meaning depends on letter case.

Reachability

Not reachable through JpmcdsMakeDateInterval or JpmcdsStringToDateInterval, both of which upper-case first and normalise 'Y' to months. It bites hand-constructed TDateInterval values — which is precisely the audience upstream’s own comment names, a few lines above the defect:

This code is left here for people who have set up their own TDateIntervals without calling JpmcdsMakeDateInterval or one of the supplied macros.

Status in the port

Cannot occur. make_date_interval upper-cases and normalises to days or months before any arithmetic, so no non-canonical period type survives to the calculation. 

Port: make_date_interval(1,'y') == make_date_interval(1,'Y') -> true
Tests: DateIntervalDifferential.Upstream3_LowercaseYAdvancesQuarterlyNotAnnually
        DateIntervalMake.IsCaseInsensitiveIncludingY
The first asserts the defect still exists upstream, so it fails if a future release fixes it.
UPSTREAM-4

Stack buffer overflow from string input

High · memory safety Fixed · deliberate divergence

lib/src/convert.c:288 · JpmcdsStringToDateInterval

Mechanism

The digit-copy loop has no bounds check against its fixed stack buffer:

#define MAX_DIGITS 32
char numberBuff[MAX_DIGITS];
char *nump = numberBuff;
...
while (isdigit((int)*inp))
    *nump++ = *inp++;          /* unbounded */

UPSTREAM-8

A validation guard that validates almost nothing

Low · a guard that does not guard Resolved · guards the real failure

contingentleg.c:90 & :97, feeleg.c:101 & :108 — the same line, four times

Mechanism

if (!JpmcdsZeroPrice(spreadCurve, cl->endDate) > JPMCDS_LOG0_THRESHOLD)
{
    JpmcdsErrMsg("%s: Default hazard rate is not defined at maturity %s!", ...);
    goto done;
}

! binds tighter than >, so this is (!price) > 1e-100 — a 0 or 1 compared against a threshold. True exactly when the price is zero. The intent was plainly !(price > THRESHOLD): reject a survival probability too small to take a logarithm of. The macro is even named JPMCDS_LOG0_THRESHOLD, "Used for avoiding LOG0 error".

Evidence

hazard rate    survival(T)    as-written as-intended JpmcdsContingentLegPV
0.01           0.905          passes    passes    pv=494850
0.5            0.00671        passes    passes    pv=5.63225e+06
5              1.85e-22       passes    passes    pv=5.96421e+06
20             1.17e-87       passes    passes    pv=5.99101e+06
50             4.72e-218      passes    fires     pv=5.9964e+06
80             0              fires     fires     REJECTED
200            0              fires     fires     REJECTED

Why the severity is low, stated carefully

The window where written and intended behaviour differ is survival in (0, 1e-100] — hazard rates above roughly 23 for a ten-year maturity. That is not a credit; it is a number that has underflowed.

And in that window the computation does not misbehave. At a hazard rate of 50 it returns 5.9964e6 against a notional of 1e7 and recovery of 0.4 — that is notional × (1 − R) = 6e6 to four figures, the correct limit for a credit certain to default. The guard was defensive, the defect disabled the defence, and the computation turned out not to need it.

So this is not a demonstrated mispricing, and it is recorded as a guard defect rather than a numerical one — precisely because the tempting headline, "precedence bug on the pricing path", would overstate it.

Status in the port: resolved, by measurement

The port guards the real failure rather than a proxy. It computes, and rejects a result that is not finite. 1e-100 was only ever a stand-in for "the logarithm will misbehave"; with the integral built, that condition is directly testable.

The measurement: down to survival probabilities around 1e-300 the logarithms stay finite and the integral converges on notional × (1 − recovery) — the correct limit for a credit certain to default. Only an exactly zero survival gives log(0) = −inf and a NaN. So the honest guard and upstream's broken one fire on identical inputs, verified from hazard 0.001 to 200 across the boundary where survival crosses from tiny to underflowed.

Upstream's behaviour is therefore preserved while the stated condition is true. Implementing the author's literal intent would have made the port refuse to price cases upstream prices correctly — which is why "fix the contract violation" was the wrong reflex, and why this decision waited for a measurement.

Reproduce: ./build/debug/defect_evidence u8
UPSTREAM-9

An error message formatted with one argument too few

Medium · undefined behaviour on a reject path Cannot occur

stub.c:173, inside JpmcdsStringToStubMethod

Mechanism

One message is declared with two %s conversions:

static char invalidFormatMsg[]  = "%s: Invalid stub method format %s. "
    "Format is LOCATION/TYPE/[LENGTH].\n" ...

The bad-LOCATION branch passes both arguments. The bad-LENGTH branch, twelve lines below it, passes one:

JpmcdsErrMsg (invalidFormatMsg, routine, name);   /* correct   */
JpmcdsErrMsg(invalidFormatMsg, routine);          /* one short */

So vsprintf reaches for a second argument that was never pushed, takes whatever occupies that varargs slot, and dereferences it as a string. Any input whose LENGTH field is present but does not begin with s, S, l or L reaches it — including "f/", where the field is present but empty.

Evidence

AddressSanitizer: stack-buffer-underflow, READ of size 5
  #0 strlen                      <- consuming the second %s
  #3 __vsprintf_chk
  #5 JpmcdsErrMsgV
  #7 JpmcdsStringToStubMethod+0x120

On manifestation, stated carefully

The read is undefined whenever the branch is taken, but whether it faults depends on what the caller left in that varargs slot. Measured on arm64 macOS it faults in a minimal standalone frame, and does not fault inside the differential test binary or inside the evidence tool.

A dedicated reproducer target was written and then deleted, because it stopped faulting once it was a CMake target rather than a scratch file — the frame layout changed and the slot stopped holding a poisoned address. So the evidence here is the source, not a crash. Behaviour that appears in one caller and not another is what undefined behaviour looks like; that is not grounds for calling it benign, and not grounds for claiming a reliable crash either.

A documentation divergence found alongside it

The same message documents the format as LOCATION/TYPE/[LENGTH] — three fields. The parser splits on a single / and reads field two as LENGTH. There is no TYPE field, and a third field is silently ignored: "f/n/l" is read as LENGTH 'n' and rejected without ever reaching the 'l'. The code is the specification; the message describes an interface that was never built.

Status in the port

Cannot occur. parse_stub_method returns nullopt and formats nothing. It also drops upstream's toupper(*locStr) call — whose domain excludes negative values, i.e. any byte above 0x7F where char is signed — in favour of comparing both cases directly.

Two upstream behaviours are kept on purpose: single-character field matching, so "fromage/sausage" still parses as front/short, and the "f"-succeeds / "f/"-fails asymmetry, which comes from upstream distinguishing a missing field from an empty one. Both are observable at a public API.

UPSTREAM-10

Unbounded vsprintf into a 4096-byte stack buffer

Medium · caller-controlled stack overflow Cannot occur · no error log exists

cerror.c:533 — the one function every formatted error message passes through

Mechanism

static int JpmcdsWriteToLog(TBoolean formatted, char *format, va_list parminfo)
{
    char buffer[JPMCDS_ERR_MSG_BUFFER];   /* 4096 */
    ...
    if (formatted)
    {
        vsprintf(buffer, format, parminfo);
    }

vsprintf, not vsnprintf. Of the 452 JpmcdsErrMsg call sites, 67 interpolate a caller-supplied string after the routine name — day count strings, date interval strings, stub strings, calendar and file names. A caller passing roughly 4KB or more of string writes past the end of this buffer with content it chose.

Evidence

Measured threshold, two independent public entry points, messages enabled. The prefix is about 200 characters, so the cliff lands where prefix plus argument reaches 4096: 

length   JpmcdsStringToStubMethod      JpmcdsStringToDayCountConv
1000     returns FAILURE               returns FAILURE
3800     returns FAILURE               returns FAILURE
3900     ABORT (fortify check fires)   ABORT (fortify check fires)
4200     ABORT                         ABORT
9000     ABORT                         ABORT

Survives at 3800, dies at 3900, identically from both entry points. On a fortified libc the overflow is detected and the process aborts; on an unfortified build it is a plain stack smash with caller-controlled bytes.

Why Medium and not High

The formatting is only reached once a host has called JpmcdsErrMsgOn. Messages are off by default and nothing in the shipped distribution turns them on — with messages off, a 50,000-character argument is harmless.

So it is latent in the library and live in any host that enabled diagnostics — which is exactly the configuration someone debugging a pricing discrepancy would be running, and the configuration an Excel add-in surfacing error text would want.

How it was found, because the route matters

This is the mechanism that makes UPSTREAM-9 more than a cosmetic slip: the stray pointer U9 produces is dereferenced by this same vsprintf. U9 supplies a bad pointer; U10 is the unbounded write it feeds.

Finding them in that order was luck. U9 was visible by reading stub.c while porting the stub parser. U10 only appeared because U9's reproducer behaved inconsistently, and the question "why does this sometimes fault" led into cerror.c. An inconsistent reproducer turned out to be a more useful signal than a reliable one would have been.

Status in the port

Cannot occur — and not because it was fixed. There is no global error log to format into: a failure is an empty std::optional, and a caller-supplied string is never copied anywhere. The defect is absent structurally rather than patched, which is the fifth time in this port that a defect died from the shape of the code rather than from a correction.

UPSTREAM-11

A negative accrual, returned as SUCCESS

High · a wrong cash amount, reported as success Fixed · documented intent

defaulted.c:68–80, inside JpmcdsDefaultAccrual

The only defect in this register that silently returns the wrong money. Not undefined behaviour, not a crash, not an error path — a settlement amount.

Mechanism

The function locates the coupon period by the trade date and then accrues to the event date: 

while (i < fl->nbDates)
{
    if (fl->accStartDates[i] <= tradeDate && tradeDate < fl->accEndDates[i])
    {
        *accrualDays = edd + 1.0 - fl->accStartDates[i];

It guards edd >= startDate, but never edd >= accStartDates[i]. So as soon as the trade date crosses a coupon boundary the event date did not, that subtraction goes negative — and status = SUCCESS is set on the next line.

Evidence

Quarterly from 20 March 2024, credit event 1 August 2024, notional 1e7, coupon 100bp, ACT/360. The event sits in the 20 June – 20 September period, so 43 days are owed. Varying only when the question is asked: 

  trade date       upstream   accrual days   amount           port
  event+0          SUCCESS    43             11944.4          43 days
  event+14         SUCCESS    43             11944.4          43 days
  event+45         SUCCESS    43             11944.4          43 days
  event+50         SUCCESS    -49            -13611.1         43 days
  event+90         SUCCESS    -49            -13611.1         43 days
  event+365        SUCCESS    -322           -89444.4         43 days

The flip lands exactly where the trade date passes 20 September.

Scope

event dates across Apr-Dec 2024, settlement lags 0-120 days:
  2250 cases, 1399 (62%) differ from asking on the event date,
  1345 (60%) return a NEGATIVE accrual.

Why High — and why the sign is not the argument

A negative accrual is obviously wrong, and a careful caller might catch it. The real problem is the dependence: the coupon accrued at a credit event cannot depend on when someone asks. Upstream's answer does, and in the window before the sign flips it is wrong without being obviously wrong.

Settlement after a CDS auction routinely lands weeks after the event determination date. A quarterly coupon boundary sits every 13 weeks. The affected regime is not an edge case; it is the ordinary one.

Status in the port

Fixed. One date changed: the period containing the event date is located rather than the one containing the trade date. The period start then precedes the event by construction, the result is always positive, and it no longer varies with the trade date. The arithmetic, the conventions and the trade < event gate are all upstream's, untouched.

A second change follows from the same root cause and is recorded rather than absorbed: upstream fails when the trade date lies past the final accrual end, because no period contains it — even though the event sits inside the schedule and the debt is well defined. Locating by the event date means a late settlement still returns what is owed. Intended, but a divergence rather than a sign fix.

Because this module corrects rather than reproduces, its recorded vectors are the documented intent, each flagged with whether upstream agreed when they were generated: 859 of 1,302 agreed, 443 did not. The differential suite asserts the disagreement still exists, so an upstream fix becomes visible rather than leaving a correction nobody revisits.

UPSTREAM-12

A lunar-month interval computes correctly, then fails

Low · reachable only via a hand-built interval Cannot occur

date_sup.c, inside JpmcdsDateIntervalToYears

Mechanism

case 'U':
    *years = (double)interval->prd *
             (double)JPMCDS_DAYS_PER_LUNAR_MONTH/JPMCDS_DAYS_PER_YEAR;
default:                        /* no break above */
    JpmcdsErrMsg("%s: unknown interval type %c.\n", routine, interval->prd_typ);
    return FAILURE;

Second of its family after UPSTREAM-5.

Evidence

type   rc         years          note
A      SUCCESS    1              annual
M      SUCCESS    0.08333333333  monthly
D      SUCCESS    0.002739726027 daily
U      FAILURE    0.07671232877  LUNAR MONTH
Z      FAILURE    -999           genuinely unknown

28/365 = 0.07671232877  <- what 'U' computes before falling through

The last row is the one that matters. A genuinely unrecognised letter leaves the output untouched at its sentinel; 'U' writes the correct value and then returns FAILURE. The computation ran; only the break is gone.

Reachability, stated precisely

This is low severity for one reason, and the first draft of this entry overstated it before the reachability was measured. JpmcdsMakeDateInterval('U') normalises to 28 days, so an interval built the way callers build one reaches the ACT/365F branch and works. The missing break is reachable only through a hand-constructed TDateInterval.

That is not hypothetical — upstream contemplates it. The switch in JpmcdsDtFwdAny retains code for 'A', 'S' and 'Q' with the comment "left here for people who have set up their own TDateIntervals without calling JpmcdsMakeDateInterval". It extends that courtesy to 'W' and not to 'U', so a hand-built lunar interval is refused by one function and mishandled by the other.

It propagates as far as it can: JpmcdsDateIntervalToFreq and JpmcdsCountDates both consume this function.

Status in the port

Cannot occur. make_date_interval('U') yields {28 × periods, Days}, so no DateInterval ever carries the unit letter the bug keys on, and interval_to_years has two total branches where upstream has eleven partial ones.

The equivalence that makes that safe is checked rather than argued: for every letter the parser accepts, the normalised interval's year fraction is compared bit-for-bit against what upstream computes from an interval built through its own constructor. Normalisation divides numerator and denominator by the same factor — 'Q' with 5 periods becomes 15 months, and 15/12 is exactly 5/4 — so the correctly-rounded quotient is unchanged, across 120 recorded cases.

UPSTREAM-13

A leaked global that disables validation process-wide

Medium · one failed call, permanent effect Cannot occur

lintrp1.inc, expanded as JpmcdsLinInterpLongPoint1Discontinuous

Mechanism

Upstream cannot say "search without checking order" per call, because that choice lives in a mutable global: bSearchCheckOrder_g in bsearch.c, default TRUE, consulted by both JpmcdsBSearchDouble and JpmcdsBSearchLong before validating that their input array is sorted.

The discontinuous interpolator legitimately needs the unchecked search — repeated abscissae are the discontinuities — so it clears the global, checks order itself, searches, and restores it: 

checkOrder = JpmcdsBSearchCheckOrder(FALSE);
if (checkOrder)
{
    for (idx = 0; idx < N-1; idx++)
        if (XARRAY(idx) > XARRAY(idx+1))
        {
            JpmcdsErrMsg(...);
            return FAILURE;                     /* leaks */
        }
}
if (SEARCH_ROUTINE_NAME(xDesired, x, xskip, N, &lo, &hi) == FAILURE)
    goto done;                                  /* leaks */
JpmcdsBSearchCheckOrder(checkOrder);            /* only on success */

Both error paths leave before the restore.

Evidence

  baseline:                      JpmcdsBSearchLong(unordered) -> FAILURE (validated)
  one failed call ...            -> FAILURE
  after that single failed call: JpmcdsBSearchLong(unordered) -> SUCCESS  *** VALIDATION IS OFF ***
  current global state:          FALSE (leaked)

Scope

Afterwards, every binary search in the process stops checking that its domain is sorted — including inside the zero curve and the whole CDS pricing path. A binary search over an unsorted array does not fail; it returns a bracket that is simply wrong, and the interpolation built on it is silently wrong too.

Medium rather than high, for reachability rather than consequence: the function has no caller inside the library and no declaration in any public header — but it is an exported symbol and it is in the XLL's surface, so a spreadsheet can reach it.

The clearest statement of the problem is operational: this module's differential suite has to restore the global in TearDown, or one test corrupts every test after it.

Status in the port

Cannot occur. bracket and bracket_checked are two functions and there is no global at all. That was a taste judgement made in the first slice of this port, whose comment read "process-wide state that silently changed the behaviour of every caller". UPSTREAM-13 is that sentence turning out to be literally true — not through explicit toggling, but through a leak.

UPSTREAM-14

Bond metrics return stack garbage before the epoch

Medium · uninitialised read, wrong answer, reports success Cannot occur · port is correct

yearfrac.c — bondDaysDiff / bondEDaysDiff, behind JpmcdsDayCountToMetricFunc

Mechanism

static double bondDaysDiff(double startDate, double endDate)
{
    long days;                                        /* uninitialised */
    (void)JpmcdsDaysDiff((TDate)startDate, (TDate)endDate,
                         JPMCDS_B30_360, &days);
    return ((double)days);                            /* garbage if it failed */
}

The status is discarded. JpmcdsDaysDiff fails for a TDate before the 1601 epoch and does not write its out parameter, so the metric returns whatever was on the stack.

Evidence

DaysDiff(-50  , 100, 30/360) -> FAILURE  days = -123456789 <- OUT PARAM NEVER WRITTEN
DaysDiff(0    , 100, 30/360) -> SUCCESS  days = 100

metric(-50, 100) -> 6101050560          <- uninitialised stack read

interpolate at -50 with the 30/360 metric -> -667794.1351

The curve interpolated is f = {0.01, 0.02}, and JpmcdsLinInterpLongPoint1 reports SUCCESS.

The value is not stable, and that is the point. A second binary built from the same sources gave metric(-50, 100) = 4 and an interpolated −619018.2639. Whatever occupies that stack slot is what the caller gets, so any single figure above is one observation rather than the answer.

Two notes on how it was found

It is an uninitialised read, which AddressSanitizer cannot detect — MemorySanitizer would, and this project does not run one. The sanitizer job is green on it.

And it was found by the golden generator's full cross-product of abscissae against metrics, not by the differential suite, whose sweeps used realistic dates for each metric. A generator that sweeps everything found what targeted sweeps missed.

Status in the port

Cannot occur, and the port additionally diverges by being correct. metric_distance checks the status it is given, so a failure becomes nullopt. In practice the branch rarely fires: std::chrono has no 1601 epoch, so a pre-epoch abscissa is simply a date in 1600 and the 30/360 difference is well defined. The port returns a sensible extrapolation where upstream returns garbage.

The recorded vectors deliberately omit the affected combinations. Recording the output of undefined behaviour would enshrine it — the same rule that kept UPSTREAM-4's buffer overflow out of the vectors.

UPSTREAM-15

A validating constructor that admits unpriceable curves

Medium · a silent NaN where an error belongs Cannot occur

tcurve.c — checkTCurve, reached through JpmcdsMakeTCurve

Mechanism

checkTCurve's stated purpose is "to guarantee we can generate positive discount factors". It checks the day count with JpmcdsDayCountValid, which correctly accepts 30/360 — a thoroughly standard convention — and it accepts an empty curve, since its only size test is fNumItems < 0.

Neither can be priced. JpmcdsZeroPrice routes through JpmcdsConvertCompoundRate, which supports ACT/365F and ACT/360 and rejects everything else explicitly. And JpmcdsZeroPrice returns a bare double, so it has nowhere to report the failure.

Evidence

ACT/365F   construct=accepted  JpmcdsZeroPrice=0.7833167239
30/360     construct=accepted  JpmcdsZeroPrice=nan
30E/360    construct=accepted  JpmcdsZeroPrice=nan
empty      construct=accepted  JpmcdsZeroPrice=nan

So a caller picks a standard day count, a constructor named Make… with an explicit validation pass accepts it, and every discount factor afterwards is NaN. The same problem as UPSTREAM-2 in a different disguise: there is no error channel, so the error becomes a number.

The distinction that matters

Infinity is not part of this finding, and conflating the two would overstate it. A continuous-basis rate of −400 over three years is exp(1200), which overflows to +inf in upstream and in the port alike — both accept the curve and both return the same infinity. That is a value: the answer is enormous. NaN is not a value; here it is an error channel.

Status in the port

Cannot occur. ZeroCurve::create rejects at construction what cannot be priced: a non-empty curve is required, and the day count must be one the conversion supports. That is why create is deliberately stricter than checkTCurve on those two counts, and why zero_price can return a plain double with no NaN sentinel — every curve that exists can be priced.

The guarantee is pinned as a tier-1 property over 810 discount factors drawn from the curves create accepts: never NaN, non-negative, and finite for any rate a market could quote.

And what else was dropped

JpmcdsMakeTCurveNoRateCheck treats a TDate of 0 as an array terminator — "This allows spreadsheet users to select a big range of dates, but use less than the whole range by terminating with a 1 or 0." Measured: five dates with a zero at index 2 produce a curve of two points.

Not reproduced. The port takes a std::span, so the length is explicit and a terminator has nothing to mean — and date 0 is a legitimate date, 1601-01-01, that a span-based caller could reasonably include. The same input is refused outright as out of order rather than silently truncated.

UPSTREAM-7

Date list truncation is ignored when fewer than two dates survive

High · silently wrong Fixed · documented intent

lib/src/dtlist.c:592 & lib/src/cxdatelist.c:220 — two implementations

Mechanism

Both scan backwards for the truncation point:

truncatePt = -1;                       /* dtlist.c */
for (i = numItems - 1; i > 0; i--)     /* index 0 is never tested */
{
    if (dateList->fArray[i] < truncationDate) { truncatePt = i; break; }
    if (inclusive && dateList->fArray[i] == truncationDate) { truncatePt = i; break; }
}
size = truncatePt + 1;

The condition is i > 0 rather than i >= 0, so the scan can fail to find any qualifying element. When it does, the sentinel survives — and the two files chose different sentinels, so they fail in opposite directions.

The consequence is wider than element 0, which an earlier version of this report understated. The scan finds nothing whenever fewer than two dates should survive, so dtlist.c returns an empty list while cxdatelist.c ignores the truncation entirely.

Evidence

  input / cut                want           dtlist.c         cxdatelist.c
                                            (sentinel -1)    (sentinel n-1)
  [1,2] @2                   [1]            []               [1,2]
  [10,30] @30                [10]           []               [10,30]
  [5] @9                     [5]            []               [5]
  [9,10] @9 inclusive        [9]            []               [9,10]
  [1,2,3] @3                 [1,2]          [1,2]            [1,2]
  keep-before                  want         cxdatelist.c
  [5,6,7] @3                   []           [5,6,7]      <- ignored entirely
  [5,6,7] @5                   []           [5,6,7]
  [5,6,7] @6                   [5]          [5,6,7]
  [5,6,7] @7                   [5,6]        [5,6]        correct

  keep-after also fails when the answer is empty:
  [5,6,7] @9 keep-after        []           [5,6,7]

Over a 600-case sweep across six lists, every cut position and both directions, upstream disagrees with the documented intent on 234 cases — 39%. Both are correct whenever two or more dates survive, which is the common case and the reason this has gone unnoticed.

Reachability

The cxdatelist.c variant is called from timeline.c, which builds the integration timeline for the fee and contingent legs — so it sits on the CDS pricing path.

Price impact: measured, and it is none. timeline.c is the only caller on the pricing path, and it cannot reach the defect. Both of its truncations run after the start and end dates have been merged into the list, and the contract requires end > start, so at least two distinct dates always survive — precisely the regime where upstream's truncation is correct.

Confirmed over 96 integration windows plus 8 deliberately minimal two-date timelines, every one matching the corrected port exactly. Note the form of that answer: the sweep says the defect did not bite in the cases tried, while the structural argument says it cannot bite at all.

Status in the port

Fixed. The port implements the documented intent. This was the first finding where "preserve upstream behaviour" was not available — there are two upstream behaviours and they contradict each other as well as their own header — and it prompted the project to write down a policy for when a port corrects rather than reproduces. Recorded vectors for this module hold the intended answers plus a flag for whether upstream agreed, so the correction stays visible instead of becoming invisible. The price impact is owed a measurement when timeline.c is ported.

Reproduce: ./build/debug/defect_evidence u7
UPSTREAM-6

Business-day adjustment never returns

High · liveness Cannot occur in the port

lib/src/busday.c · getNextBusDate

Mechanism

The walker steps one day at a time with no iteration bound:

aHoliday = TRUE;
do
{   /* Check if it's a holiday first. */
    ...
        if (JPMCDS_IS_WEEKEND (curDate, hl->weekends))
             curDate += direction;
        else
             aHoliday = FALSE;
    ...
}
while ( aHoliday == TRUE );

If the calendar's weekend set covers all seven days, aHoliday never becomes FALSE and the loop never exits. Such a calendar is accepted: JpmcdsHolidayListNewGeneral(NULL, 0x7F) returns a valid list, because verifyHolidayList has no opinion on the weekend mask.

Evidence

calendar with weekends=0x7F constructed: accepted
calling JpmcdsHolidayListBusinessDay with FOLLOW...
--- killed after 5s ---

Reachability

Needs all seven weekend bits set, for which upstream provides no named constant — a caller would have to OR them or compute the mask. So it is a robustness failure rather than a likely production path. But accepted input that never returns is the kind of defect that takes a pricing service down rather than returning a wrong number. As it spins, curDate += direction would eventually overflow TDate as well; the hang simply arrives first.

Status in the port

Cannot occur. roll_to_business_day returns nullopt when any calendar has no business weekday, and otherwise bounds its loop at 7 × (holidays + 2) — a ceiling derived from the fact that stored holidays are always business weekdays and reaching the next one costs at most seven days.

Construction stays permissive, matching upstream, because the predicates are well defined for such a calendar: everything is a non-business day. Calendar::allows_business_days() exposes the condition.

Only half of this is differentially testable. A test asserts upstream still accepts the calendar, and fails if a future release rejects it — but it cannot assert the hang, because the test would never finish.

UPSTREAM-1

Month validated after it indexes a 13-element table

Low · UB on a reject path Cannot occur in the port

lib/src/dateconv.c:657 · JpmcdsMDYToDate

Mechanism

The day-range check indexes the month-length table before the month-range check has validated month: 

/* Make sure day is in range. */
if (day >= 1 && day <= 28)
   /*EMPTY*/;
else if (day < 1 ||
    (isLeap ? day > leapDays[month] : day > (days[month])))   /* month unvalidated */
{ ... return FAILURE; }

/* Make sure month and year are in range. */
if (month < 1 || month > JPMCDS_MONTHS_PER_YEAR || ...)       /* too late */
{ ... return FAILURE; }

days[] and leapDays[] hold 13 elements, so month == 13 reads one past the end.

Evidence

ERROR: AddressSanitizer: global-buffer-overflow
READ of size 4 at 0x000102977db4 thread T0
    #0 JpmcdsMDYToDate dateconv.c:658
0x000102977db4 is located 0 bytes after global variable 'leapDays' ... of size 52

Reachability

All three conditions must hold:

  • the year is outside 1995–2119 — inside that window gDateCacheArray’s fast path validates the month first and returns early, hiding the defect
  • day >= 29 — day <= 28 short-circuits before the lookup
  • month > 12

The same validation logic appears in JpmcdsNormalizeMDY with the ordering correct: it normalises month into 1–12 before indexing. One defect, written twice, right in one copy.

Status in the port

Cannot occur. make_date range-checks before constructing anything, and days_in_month takes a std::chrono::year_month, so a 13th month cannot be represented in a value that reaches a table.

Tests: DateDifferential.MakeDateMatchesUpstreamIncludingRejections
        DateMonth.DaysInMonthIsTypeSafeWhereUpstreamWasNot
The sweep covers months 0–12 only: there is no defined behaviour at 13 to compare against.
UPSTREAM-2

JPMCDS_DEFAULT and FAILURE are both -1

Design · no caller broken today Cannot occur in the port

lib/include/isda/cgeneral.h:56 and :64

Mechanism

#define FAILURE        -1
#define JPMCDS_DEFAULT -1

A day count code of -1 means both “the default convention” and “this call failed”. The same pattern appears in JpmcdsDate, which returns FAILURE as a TDate.

Evidence

  JPMCDS_DEFAULT = -1
  FAILURE        = -1
  equal?         = YES

Upstream parse of "Default": rc=SUCCESS, code=-1
Upstream JpmcdsDate(1600,1,1) (an invalid date): -1

A caller holding a long cannot distinguish the two.

Status in the port

Cannot occur. Success and value are separate channels:

Port parse of "Default": has_value=true, value=-1
Port make_date(1600,1,1):  has_value=false

-1 is an ordinary value in the port, not a signal. This is the reason the port returns std::optional throughout rather than reserving values inside the result space.

UPSTREAM-5

Days never format as weeks

Cosmetic · output still correct Reproduced deliberately

lib/src/convert.c · JpmcdsFormatDateInterval

Mechanism

The 'D' case computes a week form and then falls through into default:, which overwrites both variables: 

case 'D':
    if (interval->prd % JPMCDS_DAYS_PER_WEEK == 0)
    {
        periodType = 'W';                     /* computed... */
        numPeriods = interval->prd/JPMCDS_DAYS_PER_WEEK;
    }
    ...
    /* no break */
default:
    periodType = interval->prd_typ;           /* ...then discarded */
    numPeriods = interval->prd;

The 'M' case directly above it does have its break, so month collapsing works.

Also noted — why the library cannot be used concurrently

Not defects in the sense above, but the reason the library is single-threaded in practice. The port holds no mutable global state.

Location State
buscache.c:62 THoliday *cache = NULL; — no static, so it has external linkage and is exported from the archive as _cache. A process-wide holiday cache with no locking.
cerror.c Eight statics including a FILE * log handle and a callback pointer
bsearch.c:19 bSearchCheckOrder_g, a global flag that silently switched every binary search in the process between checked and unchecked

bSearchCheckOrder_g is already gone — the caller chooses bracket or bracket_checked. The holiday cache becomes a value the caller owns when the calendar layer lands.

Method

The upstream C is compiled untouched into a static library and linked into the same test binary as the port. Tests call both implementations side by side and compare in-process, so the oracle is not a recorded value that can go stale — it is the original code, executing.

All of it runs under AddressSanitizer and UndefinedBehaviorSanitizer. That pairing is what surfaced UPSTREAM-1 and UPSTREAM-4: neither changes the library’s return value, so neither is visible from output alone.
