## Run 2026-11-11 (first run)

**Status: RUN 2026-11-11 — PASS.** `cdsmodel.xll` loaded in 64-bit Excel, all 24
functions registered, every pricing row matched the library and both signature
forms agreed. The recorded run is below.

C8 of `specs/03_xll.md` is the one criterion CI cannot reach: an XLL only truly
runs inside Excel, on Windows. Everything else about the add-in is tested
without it — the tests over `xl/core` cover marshalling, the registration table,
dispatch, the handle registry and both signature forms — but "it loads and
registers in Excel" is not among them.

The run below was driven over COM automation (`Excel.Application.RegisterXLL`,
open workbook, `CalculateFullRebuild`, read cells) rather than by hand. That is
the same Excel calculation engine and the same registered add-in; scripting it
only makes the evidence reproducible. A human clicking through the workbook
would see the identical Verdict and Forms columns.

## How to run it

    cmake --preset release                       # with the SDK in xlsdk/
    cmake --build --preset release --target cdsmodel_xll
    python tools/gen_xll_workbook.py             # (optional) refresh smoke.xlsx
    pwsh tools/run_c8.ps1                         # loads the .xll, prints verdicts

`tools/run_c8.ps1` drives 64-bit Excel over COM: it registers the add-in, sweeps
every function name for `#NAME?`, recalculates the workbook and prints the
Verdict and Forms columns, exiting non-zero if anything fails to register or any
row is not PASS. Or do it by hand: load `cdsmodel.xll` in 64-bit Excel, open the
workbook, let it recalculate.

### Expected values, computed from the library

These come from `tools/gen_xll_workbook.py`, which builds a program against the
same library the add-in links — no number here was typed by hand. The spread
curve is **bootstrapped** from the one 5y/100bp benchmark (not a flat 1% curve),
so the 5y/100bp contract reprices to ~0: it is the instrument the curve was
calibrated to. An earlier generator built a flat curve and its numbers
(-0.0181, -0.1514, ...) disagreed with Excel; they are superseded by the values
below, which the recorded run above reproduces to the tolerance of the sheet.

| case | expected |
|---|---|
| 5y, 100bp, ACT/360 | -2.845e-16 (~0) |
| 10y, 250bp | -0.115544454119 |
| 5y mid-period, dirty | -0.001024802294 |
| 5y mid-period, clean | 0.000002975484 |

The last two differ by 0.001027778, which is 37 days at 1% on ACT/360 — the
accrued interest. Two earlier versions of that case returned identical numbers
for clean and dirty, once because the trade started on the valuation date and
once because the valuation date landed on a coupon date. Both are dates where
accrual is zero by definition, so the case could not fail. It is now valued
mid-period on purpose.
## What to read in the sheet

The workbook is self-contained -- it builds its own curves, so there is nothing
to fill in.

| cell | what it tells you |
|---|---|
| `B9` | the add-in loaded and dispatched at all |
| `B6` / `B7` | the curve builders worked. A handle like `USD#1` is success; **text is the diagnostic** and worth recording verbatim |
| column J | each price against the value the C++ library computed: PASS, or FAIL with the difference |
| column K | the 16-argument and 5-argument forms against each other: SAME, or DIFFER with the gap |

Column K is C9 checked inside Excel. Both forms read into the same four structs
and then run one code path, so a test already proves they agree bitwise off
Excel -- but that test cannot see a marshalling difference between the two
argument shapes, and this column can.

**A partial result is still worth recording.** If `B6` holds text, the add-in
loaded, registered, dispatched and returned a readable message rather than
`#VALUE!` -- which is C1, C2 and C3 demonstrated in the real host. Copy the
text; it names the field and the value.
